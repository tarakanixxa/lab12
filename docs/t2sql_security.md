# Text-to-SQL: захист і оцінювання
У демонстрації використано mock LLM adapter із контрольованим набором 10 бізнес-питань і 3 негативних/adversarial тестів. Це дає змогу відтворювати тестування без API-ключа, але не є оцінкою якості реальної зовнішньої LLM.

Захисти: SQLGlot AST parser; дозволено один кореневий SELECT; DML/DDL/COPY/команди відхиляються; автоматично додається LIMIT 500; база відкривається `read_only=True`; перед виконанням запускається EXPLAIN; встановлюється statement timeout 5 секунд. Результат порівнюється з еталонним SQL за значеннями рядків.

Метрики: частка правильних відповідей серед 10 бізнес-питань; частка безпечних серед 13 усіх тестів; середня API-вартість. Для локального mock генератора вартість API дорівнює $0.00, оскільки зовнішні виклики не здійснюються.

Ризики та обмеження:
1. Семантична неоднозначність термінів (наприклад, «випуск» може означати загальну або придатну кількість).
2. Prompt injection у тексті запиту або метаданих може спонукати модель створити небезпечний SQL.
3. Великі або складні SELECT можуть створювати надмірне навантаження; потрібні timeout, LIMIT і контроль плану EXPLAIN.
4. Синтетичні дані не відображають реальну мінливість виробництва, тому висновки не можна переносити на підприємство без перевірки.
5. LIMIT обмежує кількість рядків, але сам по собі не обмежує обсяг сканування; потрібні права read-only, timeout і контроль ресурсів.

Три негативні тести: DROP TABLE, UPDATE і запит без обмеження. DDL/DML відхиляються AST-перевіркою; необмежений SELECT проходить із доданим LIMIT.
